# 여행 후 실제 지출 (expense)

여행이 끝난 뒤 실제로 쓴 돈을 입력받아 저장하고, 확정 때 저장한 예상 경비와 비교한 리포트를 준다 (API 명세 28·29·30, 화면 08·09).
예상 경비(25)·여행 확정(26)은 같은 도메인의 `ExpenseService`에 있고, 실제 지출은 `TripExpenseService`가 맡는다.

## API

| 번호 | 메서드·경로 | 화면 | 설명 |
|------|------|------|------|
| 28 | `GET /api/trips/{tripId}/expenses` | 08-01·03 | 지출 입력 화면 (ExpenseSheet). 항목별 예상·예상 합계·희망 예산·저장한 실제 지출, 1인·전체 둘 다 |
| 29 | `PUT /api/trips/{tripId}/expenses` | 08-04·06 | 실제 지출 저장. 응답은 28과 같다 |
| 30 | `GET /api/trips/{tripId}/expense-report` | 09-01~07 | 지출 리포트. 부를 때 계산하고 저장하지 않는다 |

- 금액은 헤더 `X-Currency`(없으면 KRW)로 환산해 준다. 외화인데 환율이 없으면 `503 EXCHANGE_RATE_UNAVAILABLE`
- 오류: `404 TRIP_NOT_FOUND`, `409 TRIP_NOT_COMPLETED`(끝난 확정 여행이 아님), `409 EXPENSES_NOT_SAVED`(30, 저장 전), `400 INVALID_REQUEST`(29)

## 저장 규칙 (29)

- 금액은 오늘(서울) 이전 가장 최근 고시일 환율로 원화로 바꾸고, `basis = PER_PERSON`이면 인원을 곱해 **인원 합계**로 저장한다 (`trip_expenses.amount_krw`)
- 그 여행의 지출을 지우고 보낸 순서대로 다시 넣는다 (통째로 덮어씀). 겹친 저장이 섞이지 않게 `TripService.lockMyTrip`으로 사용자 행을 잠근다
- 여행이 없거나(404) 끝난 확정 여행이 아니면(409) 요청 값을 보기 전에 거절한다
- 입력 검사는 모두 모아 한 번에 400으로 준다
  - 항목은 1개 이상, 기타(OTHER) 말고는 항목마다 한 번
  - 기타 항목은 이름(앞뒤 공백 제외 1~50자)이 필요하다. 기타 항목 수 한도는 `koready.expense.max-other-items`(기본 10)
  - 금액은 0 이상, KRW·JPY는 정수, USD·EUR는 소수 둘째 자리까지. 원화로 바꿔 integer 범위를 넘으면 400
- 1인 금액은 인원 합계 ÷ 인원을 원 단위로 반올림한다

## 리뷰어 확인 필요

명세에서 정하지 않은 값을 아래처럼 잠정으로 정했다. 응답 모양은 바뀌지 않고, 정해지면 표시한 한 곳만 고치면 된다.

| 항목 | 잠정 규칙 | 고칠 곳 |
|------|------|------|
| 예상과 비교하는 기준값 (명세 "계산 (기준값 미정)") | 예상 범위 **가운데값** ((최소 + 최대) ÷ 2). 차이 = 실제 − 기준값 (음수면 절약), 차이 비율·예산 집행률은 기준값으로 나눈다 | `ExpenseComparison` |
| 예측 일치도·오차율 계산식 (명세 "계산식 미정") | 오차율 = \|실제 − 기준값\| ÷ 기준값 × 100, 예측 일치도 = 100 − 오차율 (0 아래로 내려가지 않음). 기준값이 0원이면 비율은 모두 `null` | `ExpenseComparison` |
| 범위 안팎(`status`) | 최소보다 적으면 `BELOW`, 최대보다 많으면 `ABOVE`, 경계값 포함 범위 안이면 `WITHIN` | `ExpenseComparison.status` |
| 인사이트 문구 (09-06, LLM 미정) | LLM 대신 **템플릿 문장**. 1인 기준으로 가장 크게 덜 쓴 항목·더 쓴 항목을 알려 준다. 예: "쇼핑에서 예상보다 1인 30,000 KRW 더 썼어요." 숫자는 계산값을 그대로 넣는다. 비교할 항목이 없으면 `null` | `TripExpenseService.insight` |
| 끝난 여행 판정 | 지금은 **종료일이 지난 확정 여행**만 받는다. 33 여행 종료(`trips.ended_at`)가 아직 없어서다. 33이 들어오면 종료한 확정 여행도 받도록 고친다 | `Trip.isCompletedOn` |
| 기타가 아닌 항목에 이름을 보낸 경우 | 400으로 막지 않고 이름을 버리고 저장한다 (DB 제약상 기타만 이름이 있다) | `TripExpenseService.toRows` |
| 08 "사전 예상"을 범위의 어느 값으로 보일지 | 서버는 범위(최소~최대)를 그대로 준다. 어느 값을 보일지는 앱이 정한다 (명세와 같음) | - |

## 리포트 계산 (30)

- 예상은 확정 때 저장한 항목별 1인 범위(`trip_cost_estimates`), 전체 기준은 인원을 곱한다
- 기타 항목은 하나(OTHER)로 더하고, 이름들은 `labels[]`로 준다
- 입력하지 않은 항목은 `actual`이, 확정 때 예상이 없는 항목은 `estimate`가 `null`이다. 둘 중 하나라도 없으면 `status`·`difference`도 `null`
- `sharePct`는 같은 기준의 실제 지출 합계 대비 비중이다
- 비교·비율은 환산 전 원화로 계산하고 결과 금액만 표시 통화로 바꾼다
